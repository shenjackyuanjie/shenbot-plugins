# DeepSeek 监测插件使用与维护

[ds_monitor.py](../plugins/ds_monitor.py) **0.5.6** 配套 Rust **ds-monitor 0.5.0**，两侧版本独立管理。
插件负责进程管理、查询和看板发布；抓取、分析及监测通知由 Rust 执行。变更见[更新日志](../CHANGELOG.md)。

## 配置与 Windows 运行副本

插件配置位于 `config/ds_monitor.toml`，包含 `binary`、`config`、`interval` 和 `publish`。

- `binary` 指向运行副本 `target/release/ds-monitor-copy.exe`，与构建产物 `ds-monitor.exe` 同目录。
  watch 锁副本，cargo 更新产物，因此可以先构建、后换文件；直接把 binary 指向产物时 update 会拒绝执行。
- Rust 以配置目录作为 cwd，保证 output/settings 等相对路径一致；构建目录单独查找有效 Cargo 清单，支持外置配置。
- 显式配置不存在、无法读取或 TOML 无效时拒绝启动，不自动生成默认模板；诊断不回显配置原文。
- `cargo clean` 会删除产物和副本，之后需重新构建、复制，或执行一次 `/monitor update`。

## 命令表

| 命令 | 行为 | 权限 |
| --- | --- | --- |
| `/monitor` | 查看插件/EXE 版本、实际进程、周期结果、发布状态和目标摘要 | 所有人 |
| `/monitor check` | 强制重启 watch，等待本轮检查结果；更新期间拒绝插队 | 所有人 |
| `/monitor on` | 开启监测；已经运行时不重启 | 所有人 |
| `/monitor off` | 暂停并撤销已排队的开启、检查及更新切换 | 管理员 |
| `/monitor sp` | 现场查询服务状态页，不重启 watch、不写 watch 缓存、不分析或发送监测通知 | 所有人 |
| `/monitor update` | 构建并更新运行副本，按原开启意图恢复；与看板发布互斥 | 管理员 |
| `/monitor deploy` | 手动导出并部署看板，也用于恢复自动发布熔断 | 管理员 |
| `/monitor last [目标] [页码]` | 读取最近变更；指定目标后每页 8 项，可连续翻页 | 所有人 |
| `/monitor fp [N]` | 读取最近 1–20 条指纹历史，默认 5 条 | 所有人 |
| `/monitor render last [目标]` | 重发已有分析的四种主题图片，不调用模型；会发送通知 | 所有人 |
| `/monitor analyze last <目标>` | 重新调用模型分析最近变更，取消分析超时，并发送通知 | 管理员 |
| `/monitor help` | 查看命令帮助 | 所有人 |

重启检查、发布、更新、状态探测、渲染与重分析入口有各自 60 秒冷却，本地 last/fp 查询不受这些冷却影响。
check 等待 `=== 本轮检查结果 ... ===`，不是分析和通知全部结束；默认最多等 300 秒。
sp 明确关闭五类网页/文档、指纹及 Release/tag/commit/npm/profile 独立目标，并清空通知出口。
查询走 Rust 的官方入口与镜像回退链路；超时、退出失败、跳过、缺少完整结果均明确报告，不用“无事发生”替代失败。

## 更新与失败恢复

1. 预占更新槽，与发布互斥；运行 `cargo build --release --bin ds-monitor`，最长 900 秒，旧 watch 继续运行。
2. 在副本同盘临时目录暂存新文件并备份旧文件；暂存失败不触碰旧副本。
3. 确认旧 watch 退出，再用 `os.replace` 原子替换；停止失败保留进程句柄并阻止替换。
4. 原先开启时启动新 watch；原先关闭时只更新文件，不自动开启。
5. 新进程启动失败或首轮结果前退出/输出中断时回滚旧文件，并按仍有效的开启意图恢复。
   回滚时若进程停不下来或替换失败，会保留旧备份并在回复中给出恢复路径。

构建失败时旧 watch 不受影响。off 或卸载会撤销排队任务，构建完成后不再擅自重启。
新进程仍活着但等待首轮结果超时，会报告“未取得结果”，不因此自动回滚。
回复失败不阻断已受理更新；线程启动失败释放占位。手动 update/deploy 遇到冲突会拒绝，不自动排队执行命令。

## 看板自动发布

`publish = true` 时，仅在检查、分析及通知结束的 `=== 本轮完成 ... ===` 后决定发布：

- `changes + fingerprint > 0` 表示看板内容变化，网页、文档和指纹都计入。
- 发布中到达的变化合并为一个待办，成功后补一次；更新期间变化留到后续周期补发。
- 缺脚本、异常、超时和部署失败都累计；连续失败 3 次后暂停自动尝试，新变化也不越过熔断。
- 管理员手动 deploy 成功后清零失败次数，恢复后续自动发布。
- 发布结论检查 HTTP 与 JSON 业务确认，部分广播失败不算全部送达；通知失败不重跑已成功的部署。
- 成功时附新增归档深链接，没有可靠新增对比时给主站链接；损坏索引不当成空历史。

状态页基线与待发通知由 Rust 持久保存，早期“只在内存、不落盘”的说明已作废；sp 仍是独立只读查询。

## 修改生效与离线验证

当前宿主支持按源码哈希扫描并重载插件；扫描时机由宿主决定，修改后先用 `/monitor` 核对插件与 EXE 版本。
插件若仍是旧版，等已有 update/deploy 返回后通过 ICA 管理机制重载；EXE 若仍是旧版，再执行 `/monitor update`。
当前宿主重载会先排空并调用旧代 on_unload，再加载新代；原始后台线程不属于宿主受管调度，重载前仍应等已有构建/部署结束。

在插件仓库运行：

```powershell
uv run --no-project --python 3.12 python -m unittest discover -s tests -p "test_ds_monitor*.py"
```

测试使用假进程、临时目录和本地 HTTP 服务，不运行真实 watch/cargo/deploy、不加载私有配置、不发送真实监测通知。

## 已知边界

- stdout 同时承载正文和控制行。完整字段、数值、代次与顺序检查不等于来源认证；彻底隔离正文伪造标记需要 Rust 转义或独立事件流。
- 五类独立快目标不在周期状态字段中，不能凭周期“无变化”断言所有监测均健康。
- 发布待办、熔断和开启意图保存在插件内存，重载会重置；新插件默认尝试启动 watch。锁只覆盖当前模块，不是跨代或跨进程事务锁。
- 卸载取消尚未执行的排队任务，不强杀已开始的构建/部署；重载前应等这些任务完成。
